# Как устроен `test_lidar_power_cut_triggers_no_data_error`

Пояснение к `tests/fault_injection/sensing/test_lidars.py` — что такое
`mrm_monitor`/`request` в параметрах функции, и что делает тело функции
по шагам.

## Параметры функции

```python
def test_lidar_power_cut_triggers_no_data_error(self, mrm_monitor, request):
```

pytest сам подставляет аргументы в тестовую функцию по их **имени** —
если параметр называется `mrm_monitor`, pytest ищет фикстуру с таким же
именем и передаёт её результат. Ничего создавать/импортировать вручную
не нужно.

### `mrm_monitor`

Это наша собственная фикстура, определена в `tests/conftest.py`:
```python
@pytest.fixture(scope="session", autouse=True)
def mrm_monitor():
    monitor = MrmRequestMonitor(container=DOCKER_CONTAINER)
    monitor.start()
    ...
    yield monitor
```
`scope="session"` + `autouse=True` значит: **один** объект `MrmRequestMonitor`
создаётся один раз в начале всего прогона тестов (до первого теста) и
живёт до самого конца. Он с самого старта в фоновом потоке непрерывно
слушает топик `/safety/mrm_request` (через `docker exec ... ros2 topic
echo`) и хранит **последнее полученное сообщение** в памяти.

Когда тест получает `mrm_monitor` как параметр — это ссылка на тот самый
единственный работающий объект. Через него тест:
- читает текущее состояние топика (`get_fields`, `get_error_codes`, `get_stamp`);
- умеет "ждать" появления нужного изменения (`wait_for_error_code`,
  `wait_for_mrm_type_change`) — без необходимости самому писать цикл
  опроса топика.

### `request`

Это **встроенная** фикстура самого pytest (не наша, есть в любом pytest-проекте
по умолчанию). Даёт доступ к "текущему тесту как объекту". В этом файле
используется для одной вещи: записать на объект теста произвольные
атрибуты —
```python
request.node.expected = "..."
request.node.actual = "..."
request.node.reaction_ms = "..."
```
Эти атрибуты сами по себе никак не влияют на прохождение теста — но их
потом читает хук `pytest_html_results_table_row` в `conftest.py` и
показывает как отдельные колонки "Ожидаемый результат / Фактический
результат / Время реакции" в HTML-отчёте. Это просто способ прокинуть
информацию из тела теста в отчёт.

(В других файлах `request` также используется для
`request.getfixturevalue("some_fixture_name")` — получить фикстуру по
строковому имени динамически. В `test_lidars.py` этого нет, так как
здесь всего один тест без параметризации по списку нод.)

## Тело функции по шагам

### 1. Записать ожидаемый результат (для отчёта)
```python
request.node.expected = f"В /safety/mrm_request появляется error_code ..."
```
Чисто информационная строка для HTML-отчёта, на логику не влияет.

### 2. Снять baseline
```python
with allure.step("Снять baseline: mrm_type + активные error_codes"):
    baseline = mrm_monitor.get_fields(["mrm_type", "shadow_mrm_type", "drive_mode"])
    baseline_codes = {e["error_code"] for e in mrm_monitor.get_error_codes()}
```
- `allure.step(...)` — не логика, а просто визуальная группировка: в
  отчёте Allure это раскрывающийся блок с названием шага. Можно убрать
  без изменения поведения теста.
- `mrm_monitor.get_fields([...])` — читает **уже накопленные в памяти**
  значения полей из последнего пойманного сообщения. Не делает нового
  запроса к докеру/ROS — быстро, просто чтение переменной под локом.
- `mrm_monitor.get_error_codes()` — аналогично, парсит error_codes из
  последнего сообщения, которое уже лежит в памяти монитора.
- Строим `baseline_codes` — множество кодов ошибок, которые активны **до**
  того, как мы что-либо сломали.

Дальше — защита от "грязного старта":
```python
if LIDAR_NO_DATA_ERROR_CODE in baseline_codes:
    pytest.skip(...)
```
Если нужный код (131599) уже присутствует **до** инъекции отказа —
значит лидар уже недоступен по какой-то другой причине (как было
5 августа с `cloud_builder_node`, из-за которого `mrm_type` был равен 2
ещё до старта теста). В таком состоянии тест не может доказать, что
именно **наше** отключение реле вызвало ошибку — поэтому тест
пропускается (`pytest.skip`), а не притворяется, что прошёл.

### 3. Зафиксировать timestamp ДО отключения реле
```python
before_stamp = mrm_monitor.get_stamp()
```
Это критичный момент. Мы запоминаем timestamp **последнего** сообщения,
которое видел монитор, **прямо перед** физическим отключением питания.
Дальше (шаг 6) мы будем ждать сообщение **новее** этого timestamp — так
что даже если старое сообщение случайно уже содержит нужный код (не
должно, см. защиту выше, но на всякий случай) — тест не спутает его с
реальной реакцией на именно эту инъекцию отказа.

### 4-5. `try` / `finally` вокруг отключения реле
```python
try:
    ...
    response = relay_off()
    ...
finally:
    relay_on()
```
`relay_off()`/`relay_on()` — функции из `control_relay.py`, делают
обычный HTTP GET-запрос к физическому реле по адресу `192.168.1.120`,
которое физически размыкает/замыкает цепь питания лидара.

`try/finally` нужен, чтобы **реле гарантированно включилось обратно**,
даже если дальше упадёт `assert` или случится любое другое исключение —
иначе при падении теста лидар мог бы остаться обесточенным до ручного
вмешательства.

### 6. Дождаться появления error_code
```python
result = mrm_monitor.wait_for_error_code(
    error_code=LIDAR_NO_DATA_ERROR_CODE,
    before_stamp=before_stamp,
    timeout=10.0,
    poll_interval=0.05,
)
```
Это новый метод в `MrmRequestMonitor` (добавлен специально под этот
тест). Что он делает внутри, в цикле (максимум 10 секунд, проверяя
каждые 0.05с):
1. Смотрит, изменился ли `_latest_stamp` монитора по сравнению с
   `before_stamp` — то есть пришло ли вообще новое сообщение в топик.
2. Если пришло — парсит его через `get_error_codes()` и ищет среди них
   код `131599`.
3. Нашёл — считает время реакции (разница между timestamp'ами "до" и
   "после" в миллисекундах) и возвращает
   `{"success": True, "reaction_ms": ..., "details": ..., ...}`.
4. Не нашёл в этом сообщении — запоминает его stamp как новую точку
   отсчёта и продолжает ждать следующее (отказ может проявиться не в
   самом первом новом сообщении после `relay_off()`).
5. Если так и не нашёл за 10 секунд — возвращает
   `{"success": False, ...}`.

### 7. Проверить результат
```python
assert result["success"], (
    f"error_code {LIDAR_NO_DATA_ERROR_CODE} не появился ..."
)
```
Если код не появился за 10 секунд — тест падает с понятным сообщением
(а не просто `AssertionError` без контекста).

### 8. Записать фактический результат (для отчёта)
```python
request.node.actual = f"error_code {result['error_code_hex']} появился, reaction={result['reaction_ms']}ms"
request.node.reaction_ms = f"{result['reaction_ms']}ms"
```
Снова чисто для HTML-отчёта — те же атрибуты `request.node.*`, что и на
шаге 1.

### 9. Восстановление питания (`finally`)
```python
finally:
    relay_on()
```
Выполняется **всегда** — и при успешном прохождении теста, и при падении
`assert`, и при любой другой ошибке внутри `try` (например, если сам
HTTP-запрос к реле не пройдёт). Гарантирует, что лидар не останется
обесточенным после теста.
